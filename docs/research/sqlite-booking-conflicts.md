# Защита бронирований от пересечений в SQLite

Исследование от 8 ноября 2026 года для задачи
[«Исследовать защиту бронирований от пересечений в SQLite»](https://github.com/Gwein87/ai-for-developers-project-386/issues/5).
Это рекомендации для будущей спецификации: реализация, миграции и настройки
не изменялись. Поведение провайдера проверено по исходникам версии 10.0.0;
конкретные версии пакетов и нативной SQLite будущей реализации нужно закрепить
и проверить интеграционными тестами.

## Вывод и граница гарантии

**Рекомендация:** каждое создание бронирования выполнять короткой явной
транзакцией `BEGIN IMMEDIATE`: сначала получить право записи, затем проверить
пересечение по всем бронированиям владельца, записать и подтвердить транзакцию.
Все пути записи должны соблюдать этот протокол. Это достаточно для двух
конкурирующих запросов, даже из разных процессов; предварительное отображение
свободного слота гарантией не является.

**Факт:** SQLite допускает одного писателя на файл БД. Изоляция отдельных
соединений действует и между процессами; WAL сохраняет это ограничение,
разрешая читателям работать одновременно с писателем.
[SQLite: Isolation](https://sqlite.org/isolation.html).

**Вывод:** блокировка в памяти приложения не нужна для корректности и сама
по себе не обеспечивает её между процессами. Гарантия предполагает один общий
файл БД с исправными файловыми блокировками, отсутствие обходных путей записи
и отключённое чтение неподтверждённых данных. Она гарантирует отсутствие двух
подтверждённых пересекающихся бронирований, но не успех каждого запроса при
длительной блокировке. При необходимости защиты от записей в обход приложения
нужен дополнительный триггер, описанный ниже.

## Время и условие пересечения

**Рекомендация для первой версии:** хранить в бронировании `StartUtcSeconds`
и `EndUtcSeconds` как `long` / SQLite `INTEGER NOT NULL`, целое число секунд
Unix UTC; конец вычислять на сервере из длительности типа события в минутах
и сохранять вместе с началом. Минимальное ограничение строки —
`CHECK (EndUtcSeconds > StartUtcSeconds)`. Для внешних записей при необходимости
добавить проверку `typeof(...) = 'integer'`: обычная SQLite имеет динамическую
типизацию. SQLite документирует Unix-время как допустимый целочисленный формат.
[SQLite: Datatypes](https://sqlite.org/datatype3.html#datetime).

Часовой пояс `Europe/Moscow`, окно календарных дней, рабочие часы и сетка
стартов определяют допустимость слота в приложении; перед сравнением его
границы переводятся в UTC. Все параметры и колонки сравниваются в одной
единице без округления и без преобразования времени в SQL. Не хранить
занятость только через ссылку на текущую длительность типа события.
Это проектная рекомендация, а не требование SQLite. Альтернатива — единообразный
UTC `DateTime`; нативные сравнения `DateTimeOffset` у EF Core SQLite ограничены.
[Microsoft: ограничения провайдера SQLite](https://learn.microsoft.com/en-us/ef/core/providers/sqlite/limitations#query-limitations).

Для нового интервала `[newStart, newEnd)` пересечение существует тогда и только
тогда, когда найдена строка с
`StartUtcSeconds < newEnd AND EndUtcSeconds > newStart`.
Это вывод из требования полуоткрытых интервалов: равенство конца и начала
допускается; совпадение, частичное пересечение и вложение запрещены.
Фильтра по идентификатору типа события нет: занятость общая. В первой версии
владелец один, поэтому отдельный идентификатор владельца для этой проверки
не требуется. Индекс по началу может ускорить поиск, но не заменяет протокол.

## Транзакции .NET / EF Core

**Факты:** `DEFERRED` откладывает получение права записи. Если сначала выполнен
`SELECT`, последующее повышение читающей транзакции до пишущей может получить
`SQLITE_BUSY`. `IMMEDIATE` получает право записи до чтения и может ждать или
завершиться `SQLITE_BUSY` уже на старте. `EXCLUSIVE` для этой задачи не нужен:
вне WAL он дополнительно блокирует читателей.
[SQLite: транзакции](https://sqlite.org/lang_transaction.html#deferred_immediate_and_exclusive_transactions).

В Microsoft.Data.Sqlite 10.0.0 обычный `BeginTransaction()` выбирает
неотложенную транзакцию; явно заданные `IsolationLevel.Serializable` и
`deferred: false` приводят к SQL `BEGIN IMMEDIATE`.
[SqliteConnection.cs, v10.0.0](https://github.com/dotnet/efcore/blob/v10.0.0/src/Microsoft.Data.Sqlite.Core/SqliteConnection.cs#L458-L525),
[SqliteTransaction.cs, v10.0.0](https://github.com/dotnet/efcore/blob/v10.0.0/src/Microsoft.Data.Sqlite.Core/SqliteTransaction.cs#L19-L44).

EF Core позволяет подключить существующую `DbTransaction` через
`Database.UseTransaction` на том же соединении. Автоматическая транзакция
`SaveChanges` охватывает сохранение, но не предшествующий отдельный запрос
доступности. Savepoint внутри прежней транзакции также не заменяет новый
снимок данных.
[Microsoft: транзакции EF Core](https://learn.microsoft.com/en-us/ef/core/saving/transactions).
Токен оптимистической конкурентности проверяет изменение существующей строки;
он сам по себе не защищает от вставки другой строки с пересекающимся временем.
[Microsoft: конкурентность EF Core](https://learn.microsoft.com/en-us/ef/core/saving/concurrency).

**Рекомендуемый алгоритм одной попытки:**

1. Создать отдельные соединение и `DbContext`; начать явную неотложенную
   транзакцию до запроса пересечений и подключить её к контексту.
2. На сервере проверить тип события и допустимость слота, вычислить конец;
   проверить пересечения в БД внутри этой же транзакции. Повторно проверить
   актуальность времени, если ожидание блокировки могло сделать слот прошедшим.
3. При пересечении откатить транзакцию и вернуть понятный конфликт бронирования.
   Иначе вставить бронирование, вызвать `SaveChanges`, выполнить `COMMIT` и
   только после его успеха сообщить об успешной записи.
4. Не выполнять внутри транзакции сетевые вызовы, отправку писем или ожидание
   пользовательского ввода. Любая неуспешная попытка должна закрыть читателей,
   откатить активную транзакцию и освободить соединение.

## Блокировки, повторы и результат запроса

**Факты:** `SQLITE_BUSY` имеет основной код 5; расширенный
`SQLITE_BUSY_SNAPSHOT` — 517: в WAL читающая транзакция пытается стать пишущей
после изменения данных другим соединением. `SQLITE_LOCKED` (6) обычно указывает
на конфликт внутри соединения либо shared cache и не доказывает занятость слота.
[SQLite: коды ошибок](https://sqlite.org/rescode.html#busy_snapshot).

Microsoft.Data.Sqlite автоматически повторяет busy/locked операции до
таймаута команды; по умолчанию это 30 секунд, `0` означает отсутствие лимита.
`DefaultTimeout` действует также на внутренние команды, включая начало
транзакции. Экземпляры соединения, команды и reader нельзя использовать
одновременно из нескольких потоков.
[Microsoft: ошибки и таймауты](https://learn.microsoft.com/en-us/dotnet/standard/data/sqlite/database-errors).

**Рекомендация:** поверх ожидания провайдера ограничить число полных попыток
и общий бюджет запроса, учитывать отмену, применять короткую ограниченную
задержку со случайным разбросом. Согласовать `DefaultTimeout` и таймаут команд
с этим бюджетом: простое добавление повторов к 30 секундам резко увеличит
задержку ответа. Конкретные значения остаются решением спецификации.

После допускаемого политикой `BUSY`, включая `BUSY_SNAPSHOT`, откатить попытку
и повторить **всю** транзакцию с новым контекстом и новым чтением пересечений.
Повтор только вставки или возврат к savepoint не пересчитывает основание
решения. Для deferred-транзакций полный повтор прямо предписан документацией
провайдера.
[Microsoft: deferred transactions](https://learn.microsoft.com/en-us/dotnet/standard/data/sqlite/transactions#deferred-transactions).

Учитывать ошибку на любой стадии, включая `COMMIT`: в rollback journal
открытый читатель может помешать подтверждению, а транзакция после такого
`BUSY` остаётся активной. SQLite допускает повтор `COMMIT`; для единого простого
протокола здесь рекомендуется явный откат и новая полная попытка, если бюджет
позволяет.
[SQLite: COMMIT и активные читатели](https://sqlite.org/lang_transaction.html#implicit_versus_explicit_transactions).
Не переносить это правило на неопределённый результат подтверждения после
произвольной ошибки ввода-вывода или потери ответа.

Пользовательский конфликт возвращается только после обнаруженного пересечения
или точно распознанного защитного триггера. Исчерпание бюджета блокировки —
отдельная временная техническая ошибка, а не сообщение «слот занят».
`LOCKED`, ошибки диска и прочие исключения не следует безусловно повторять или
переводить в конфликт. При `SaveChanges` проверять вложенную `SqliteException`
в `DbUpdateException`, используя основной и расширенный коды. Конкретные
HTTP-статусы и формат ошибок должны быть согласованы в API-контракте.

## Доказательство на двух запросах

Пусть A и B хотят пересекающиеся интервалы разных типов событий:

| Момент | Соединение A | Соединение B |
| --- | --- | --- |
| 1 | Успешный `BEGIN IMMEDIATE` | Пытается начать запись, ждёт либо получает `BUSY` |
| 2 | Не находит пересечения; вставляет | Не может получить право записи |
| 3 | Успешный `COMMIT` | Начинает новую попытку после освобождения блокировки |
| 4 | Завершено | Видит бронирование A; возвращает конфликт без вставки |

Если A откатился, B может записать своё бронирование. Если B исчерпал бюджет,
он возвращает техническую ошибку. Оба пересекающихся бронирования подтвердить
нельзя: проверка второго писателя выполняется после завершения первого.
Это логический вывод из сериализации писателей SQLite, а не результат
исполненного нагрузочного теста.

## Ограничения и необязательный триггер

`UNIQUE` на начале или паре границ запрещает лишь равные значения, не
произвольные пересечения. `CHECK` годится для положительной длительности,
но его выражение не может содержать подзапрос к другим бронированиям.
[SQLite: ограничения таблицы](https://sqlite.org/lang_createtable.html#check_constraints).

**Дополнительная защита:** постоянный, не `TEMP`, триггер на `INSERT` с тем же
условием пересечения может вызвать `RAISE(ABORT, 'booking_overlap')`.
Если разрешены обновления границ, нужен также триггер на `UPDATE`, исключающий
текущую строку по первичному ключу. Не изменять строки из проверяющего триггера
и не полагаться на `NEW.rowid` в `BEFORE INSERT`. `RAISE(ABORT)` прерывает
оператор с ошибкой ограничения; приложение всё равно откатывает свою попытку.
`TEMP`-триггер не защищает записи других приложений.
[SQLite: CREATE TRIGGER и RAISE](https://sqlite.org/lang_createtrigger.html).

Вывод: такой триггер защищает инвариант и при прямых SQL-записях через другие
соединения, пока схема сохраняется и все изменения проходят через SQLite.
Распознавать именно выделенный маркер вместе с `SQLITE_CONSTRAINT_TRIGGER`
(1811), а не любое нарушение ограничения.
[SQLite: SQLITE_CONSTRAINT_TRIGGER](https://sqlite.org/rescode.html#constraint_trigger).
Для минимальной версии с единственным контролируемым путём записи достаточно
протокола приложения; выбор триггера остаётся явным решением. При его выборе
будущие миграции и перестроения таблицы обязаны сохранять эту защиту.

## Проверки будущей реализации и оставшиеся решения

Нужны интеграционные проверки с реальным временным файлом SQLite, отдельными
соединениями/контекстами и управляемыми барьерами, а не только `Task.WhenAll`
или независимыми БД `:memory:`. Рекомендуется проверить:

- Совпадение, частичное пересечение в обе стороны, вложение; соседние интервалы
  с общей границей успешно записываются. Разные типы событий используют общую
  занятость. Некорректная длительность и точность времени отклоняются.
- A удерживает транзакцию после проверки; B пытается записаться. После commit A
  B перечитывает данные и возвращает конфликт; после rollback A B получает
  успех. Проверить фактические строки в БД, а не только ответы HTTP.
- Тот же сценарий через два процесса с одним файлом; при достаточном бюджете
  ровно один успех и один конфликт, при исчерпании бюджета — отдельная
  техническая ошибка без второго бронирования.
- Блокировку дольше таймаута; ограниченность повторов, очистку транзакций и
  возможность следующего запроса успешно записаться после снятия блокировки.
- В WAL принудительный deferred-сценарий с устаревшим снимком и полным повтором;
  в rollback journal — читателя, мешающего commit. Основной протокол проверить
  в обоих режимах, если оба допускаются эксплуатацией.
- Если выбран триггер: прямой SQL в обход приложения, соседние интервалы,
  конфликтное обновление и сохранность защиты после разрешённых миграций.

До реализации остаётся выбрать бюджет ожидания и повторов, HTTP-представление
конфликта и временной ошибки, необходимость триггера и режим журналирования.
WAL может улучшить совместную работу чтения и записи, но не является условием
доказанной защиты.

Повтор HTTP-запроса после потери успешного ответа — **отдельная нерешённая
политика**. Бронирование уже могло сохраниться, а обычный повтор увидит конфликт.
Защита пересечений не позволяет определить, было ли это собственное
бронирование гостя. Ключ идемпотентности, восстановление результата или иное
поведение нельзя вводить без решения человека; оно не требуется для самого
инварианта отсутствия пересечений.
